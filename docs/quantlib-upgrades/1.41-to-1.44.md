# QuantLib 1.41 → 1.44: what changes in your numbers

Quantra 0.11.0 is 0.10.0 rebuilt on QuantLib 1.44 (0.10.0 and every earlier
release used QuantLib 1.41). There is **no request or response shape change**:
every endpoint, field, status code and error body is the same as in 0.10.0.
Some results do change, because QuantLib 1.42, 1.43 and 1.44 fixed bugs and
changed conventions in code Quantra calls. This page lists every change we
observed, who is affected (the request feature that triggers it), which
response fields move, a worked before/after number, and why — in Quantra
terms. Each item carries its upstream reference as a footnote; you do not need
to read QuantLib's release notes.

To tell which QuantLib produced a number, call `GET /meta` and read
`dependencies.quantlib` (`1.41` on 0.1.0–0.10.0, `1.44` on 0.11.0; see the
version table in [`versioning.md`](../versioning.md)).

**Corpus and coverage.** The comparison sent 291 requests to two servers
built from the *same* Quantra source, one on QuantLib 1.41 and one on 1.44:
the 208 cases of the functional catalog (`tests/functional/CATALOG.md`, every
file under `examples/data/`) plus 83 targeted probes under
`tests/version_diff/probes/` (one per upstream release-note item that could
reach the API; see that directory's README). A 1.41-vs-1.41 run of the same
corpus gave 291/291 unchanged (zero noise). Result on 1.41 vs 1.44:

| Outcome | Requests |
|---|---:|
| Unchanged (every field identical) | 215 |
| Noise only (differences ≤ 1e-12 relative) | 2 |
| Changed | 72 |
| Status changed (200 → 422) | 2 |
| Failed to compare | 0 |

"Unchanged in our corpus" is evidence, not a guarantee for every request
shape: a request with another convention, product feature, date or market
data layout can be affected by the same upstream change. Section 6 shows how
to run the same comparison on your own requests.

## 2. Changes, ordered by impact

Each verdict is one of: **upstream bug fix** (the 1.41 number was wrong),
**upstream behaviour change** (a convention or data change; neither number is
wrong), **upstream numerical change** (a different stopping point of a solver;
neither number is more accurate).

### 2.1 Cross-currency swaps and collateral curves: a compounded overnight leg on a foreign schedule calendar

**Who is affected.** A leg with `coupons_type: OvernightCoupons` and
`averaging_method: Compound` whose `schedule.calendar` is not the calendar of
its overnight index, so that an accrual date falls on a holiday of the index.
In every EUR/USD example the USD SOFR leg runs on a `TARGET` schedule while the
`USD_SOFR` index uses a United States calendar: the accrual dates 2026-01-19,
2027-01-18 and 2028-01-17 are Martin Luther King Day. The same leg sits inside
every `CrossCcyBasisHelper` pillar (the helper's `calendar` drives both of its
legs), so the `EUR_USD_COLLATERAL` curve built from those pillars moves too,
and with it everything discounted on it — including a cross-currency swap with
no overnight leg at all. Any overnight leg with the same pattern on
`/price-ois-swap`, `/price-basis-swap` or a swaption's OIS underlying is
affected the same way; none in the corpus has one, and legs whose schedule
calendar is the index calendar (every single-currency OIS example, the
`EUR_ESTR_OIS` and `USD_SOFR_OIS` curves) are unchanged.

**Fields that move.** `swaps[].legs[].npv`, `legs[].npv_reporting`,
`swaps[].npv`, `fair_spread`, `fair_rate`; on `/bootstrap-curves` the
discount factors and zero rates of the collateral curve from the 18M pillar on
(the FX-swap pillars up to 1Y are identical).

**Worked numbers.** `examples/data/cross_currency_swap/xccy_usd_sofr_vs_eur_estr_minus15bp_5y_both_exchanges.json`
(pay SOFR on 10.85m USD, receive ESTR − 15 bp on 10m EUR, both exchanges):

| Field | 1.41 | 1.44 |
|---|---:|---:|
| `legs[0].npv` (USD SOFR leg) | 3,277.96 | −1.10 |
| `legs[1].npv` (EUR ESTR leg, EUR) | 6,564.94 | 9,588.65 |
| `legs[1].npv_reporting` (USD) | 7,121.98 | 10,402.26 |
| `npv` | 10,399.94 | 10,401.16 |
| `fair_spread` | −0.00170000863 | −0.001699999997 |

The USD leg has both exchanges and is forwarded and discounted on the same
SOFR curve, so it must price at par: −1.10 on 10.85m is par (the residual is
the 2-day payment lag of the OIS helpers against the lag-0 leg). The 1.41 value
of +3,278, about 3 bp of notional, was wrong: three MLK nights of SOFR on
10.85m at roughly 4% is about 3,300. The EUR leg moves by the same amount in
the other direction because the collateral curve absorbed the same error, which
is why the total `npv` barely moves. Setting `leg1.schedule.calendar` to the
index calendar (`UnitedStatesGovernmentBond`) gives a USD leg of 8.99 on both
versions.

`examples/data/curves/curves_eur_usd_collateral_full.json` (and its
`_quote_id` twin): 14 of 50 values change, all from the 18M pillar on. The
largest zero-rate move is 0.021488854091 → 0.021414339655 (−7.5e-5); the
largest discount-factor move, at the last grid point, 0.806432698712 →
0.806841222662 (+4.1e-4).

`examples/data/cross_currency_swap/xccy_eur_fixed_vs_usd_sofr_5y_payer_usd.json`:
`npv` −225,423.22 → −225,495.55; `fair_rate` 0.02106829571 →
0.021067689937; `fair_spread` 0.004561824787 → 0.004563288478.
`examples/data/cross_currency_swap/xccy_usd_fixed_vs_eur_euribor3m_5y_receiver_eur.json`
has no overnight leg and moves only through the collateral curve: `npv`
−41,675.83 → −44,711.06, `fair_rate` 0.041932687614 → 0.04200061484. The
example `xccy_eur_fixed_at_fair_rate_vs_usd_sofr_5y.json` was struck at the
1.41 fair rate (2.106829571%) and priced to −30.82 on 1.44; in 0.11.0 it is
re-struck at the 1.44 fair rate 2.1067689937% and prices to zero again.

**Why.** QuantLib 1.41 built the daily compounding dates of such a coupon from
the accrual start rolled *forward* on the index calendar, so when the accrual
start was an index holiday compounding began on the next index business day
and the holiday night's interest was dropped. From 1.43 the previous business
day's fixing covers the holiday night. A stand-alone check of the single coupon
2026-01-19 → 2026-04-17 on a flat 4% curve (not part of the corpus) gives a
coupon rate of 3.9190% on 1.41 and 3.9643% on 1.44, and the 1.44 leg satisfies
the par identity N·(DF(start) − DF(end)) to 1 in 769,680.

**Verdict:** upstream bug fix (1.43) [^2556]. The 1.44 numbers are correct.

### 2.2 Credit default swaps on a bootstrapped credit curve: the helper trade date

**Who is affected.** A `pricing.credit.credit_curves[]` entry bootstrapped
from `quotes[]` of `quote_type` `ParSpread` or `Upfront` whose
`helper_conventions.settlement_days` is 0 and whose
`helper_conventions.date_generation_rule` is not `CDS` (every example uses
`TwentiethIMM`). Both `helper_model` values (`MidPoint`, `ISDA`) and both
pricing engines (`CdsModelSpec.engine_type` `MidPoint`, `ISDA`) move the same
way because the curve is what changed. A flat hazard-rate curve
(`tests/version_diff/probes/price-cds/cds_5y_flat_hazard_control.json`) is
unchanged. 13 of the 15 CDS cases moved.

**Fields that move.** `cds_list[].npv`, `fair_upfront`, `fair_spread`,
`default_leg_npv`, `premium_leg_npv`.

**Worked numbers.** `examples/data/cds/cds_eur_5y_buyer_100bp_spread_curve.json`
(buy 5Y protection on 10m at 100 bp running):

| Field | 1.41 | 1.44 |
|---|---:|---:|
| `npv` | 39,739.83 | 40,039.55 |
| `fair_spread` | 0.010855621907 | 0.010862108166 |
| `fair_upfront` | 0.003975556482 | 0.004005540252 |
| `default_leg_npv` | 504,195.34 | 504,477.21 |
| `premium_leg_npv` | −464,733.18 | −464,715.33 |

The move is +299.72 on the NPV (0.75%), +0.065 bp on the fair spread. Other
examples on the same curve: 10Y (`cds_eur_10y_buyer_100bp_spread_curve.json`)
227,185.13 → 227,530.28; 3Y (`cds_eur_3y_buyer_100bp_spread_curve.json`)
−18,558.56 → −18,297.79 (1.4% relative, the largest); ISDA engine
(`cds_eur_5y_buyer_isda_engine.json`) 39,758.33 → 40,058.06; 500 bp coupon
(`cds_eur_5y_buyer_500bp_running_coupon.json`) −1,818,082.20 → −1,817,711.09.
The probe whose trade is dated before the valuation date
(`tests/version_diff/probes/price-cds/cds_5y_helpers_trade_date_before_as_of.json`)
moves by the same 299.72: the trade's own `trade_date` is passed explicitly and
is not what changed.

**Why.** The curve helpers build an internal CDS per quote. Up to 1.43 that
CDS was dated on the valuation date; from 1.44 the helpers let the CDS deduce
its trade date, which for a date rule other than `CDS` is the day before
protection start. With `settlement_days: 0` protection starts on the valuation
date, so the helper trade date is now the day before it; the accrual rebate
reference and the cash-settlement date shift by one day and the par-spread
solve lands on a slightly different hazard curve. Checks on the 5Y example:
with `helper_conventions.date_generation_rule: CDS` both versions give
39,703.56; with `settlement_days: 1` both give 39,958.04. Either setting makes
the result version-independent (it does not restore the 1.41 number, which
came from a trade-date convention that no longer exists).

**Verdict:** upstream behaviour change (1.44) [^2698].

### 2.3 Overnight coupons with a lookback and an observation shift

**Who is affected.** `OvernightCoupons` with `lookback_days` greater than 0
**and** `apply_observation_shift: true`, on any endpoint with an overnight leg
(`/price-ois-swap`, `/price-basis-swap`, `/price-cross-currency-swap`, a
swaption's OIS underlying). Request variations on both versions: lookback
only, lockout only, observation shift without lookback, and lookback with
lockout are all unchanged; lookback with observation shift (with or without a
lockout) moves.

**Fields that move.** `legs[].flows[].rate`, `flows[].amount`,
`flows[].present_value`, `legs[].npv`, `npv`, `fair_rate`, `fair_spread`.

**Worked numbers.** `tests/version_diff/probes/price-ois-swap/ois_lookback2_lockout2_observation_shift.json`
(ESTR leg, `lookback_days: 2`, `lockout_days: 2`, `apply_observation_shift: true`, 5 bp spread):

| Field | 1.41 | 1.44 |
|---|---:|---:|
| `legs[1].flows[0].rate` | 0.028360390741 | 0.028513050417 |
| `legs[1].flows[0].amount` | 28,911.84 | 29,067.47 |
| `legs[1].npv` | 54,964.62 | 55,115.90 |
| `npv` | 442.80 | 594.09 |
| `fair_rate` | 0.028227404483 | 0.028305097625 |
| `fair_spread` | 0.000272595517 | 0.000194902375 |

**Why.** With an observation shift, 1.41 compounded the fixings over the
shifted dates but accrued over the unshifted dates and applied the lookback
only to the last fixing, so the coupon lost its lookback window — about two
days of interest out of a year for a 2-day lookback (a stand-alone annual
ESTR coupon on a flat 2.8% curve, not part of the corpus: 2.84027% plain,
2.82466% with lookback and shift on 1.41, 2.84012% on 1.44). From 1.43 the
compounding and the accrual use the same shifted dates.

**Verdict:** upstream bug fix (1.43) [^2556]. 1.41 under-stated these coupons.

### 2.4 Inflation swaps and caps/floors

Two upstream changes from 1.42 act here; both were already visible on 1.43.
All 9 year-on-year caps/floors, 5 of 6 year-on-year swaps and 9 of 11
zero-coupon inflation swaps moved.

**(a) Pillar placement of interpolated helpers.** Who: an inflation curve
(`pricing.inflation.inflation_curves[]`) whose helpers have
`observation_interpolation: Linear`, priced for a trade whose observation
dates fall between the helper pillars — a trade `observation_lag` different
from the helpers' `swap_observation_lag` (6M against 3M), dated helpers, every
year-on-year swap and cap/floor. A trade aligned with a helper reprices
identically (`examples/data/inflation/zciis_eur_5y_payer_linear_obs.json`
moves by 5.7e-9, noise; `zciis_eur_10y_payer_linear_obs.json` by 4.9e-10).
Fields: `swaps[].npv`, `inflation_leg_npv`, `yoy_leg_npv`, `fair_rate`,
`fair_spread`; `cap_floors[].npv`, `atm_rate`. Worked numbers:

| Request (`examples/data/...`) | Field | 1.41 | 1.44 |
|---|---|---:|---:|
| `inflation/zciis_eur_5y_payer_6m_observation_lag.json` | `npv` | −3,350.29 | −3,363.95 |
| same | `fair_rate` | 0.021716900016 | 0.021719819974 |
| `inflation/zciis_eur_5y_payer_dated_helpers.json` | `npv` | −3,542.27 | −3,496.55 |
| same | `fair_rate` | 0.021757920582 | 0.021748152037 |
| `inflation/yyiis_eur_5y_receiver_annual.json` | `npv` | −2,285.59 | −2,285.42 |
| same | `fair_rate` | 0.021999998316 | 0.021999961555 |
| `inflation/yyiis_eur_3y_receiver_semiannual_30360.json` | `npv` | −580.29 | −576.26 |
| same | `fair_rate` | 0.021203467139 | 0.02120205393 |
| `inflation_cap_floor/yoy_cf_eur_5y_cap_150bp_black_bites.json` | `npv` | 31,885.24 | 31,851.91 |
| same | `atm_rate` | 0.021975257852 | 0.021967966093 |
| `inflation_cap_floor/yoy_cf_eur_5y_floor_300bp_black_bites.json` | `npv` | 36,682.63 | 36,715.96 |
| `inflation_cap_floor/yoy_cf_eur_5y_cap_150bp_bachelier.json` | `npv` | 36,137.79 | 36,107.66 |
| `inflation_cap_floor/yoy_cf_eur_3y_cap_175bp_udblack.json` | `npv` | 21,247.15 | 21,197.18 |
| `inflation_cap_floor/yoy_cf_eur_5y_cap_280bp_black_otm.json` | `npv` | 0.111 | 0.130 |
| `inflation_cap_floor/yoy_cf_eur_5y_collar_black.json` | `npv` | 10.90 | 13.14 |

The last two are the large relative moves in the headline table: an
out-of-the-money cap and a collar whose legs nearly cancel, both worth a few
cents to a few euros on 1m notional.

Why: from 1.42 the curve node of an interpolated inflation helper is the one
that carries most of the interpolation weight — the first of the lagged
observation month when the helper's start date falls in the first half of its
month, otherwise the first of the next month — instead of always the end of
the interpolation period. The node rates are re-solved so that each helper
still reprices, and anything interpolated between nodes moves with them.
Verdict: upstream behaviour change (1.42) [^2456].

**(b) Fixed leg of a zero-coupon inflation swap accrues on the contract
dates.** Who: a `zero_coupon_inflation_swap` whose `start_date` /
`maturity_date` differ from the dates of the curve helper with the same tenor,
most visibly with `observation_interpolation: AsIndex`. Worked numbers,
`examples/data/inflation/zciis_eur_3y_payer_asindex_obs.json` (start
2025-01-15, maturity 2028-01-15; the 3Y tenor helper matures 2028-01-17 because
3Y from the valuation date lands on a Saturday and rolls):

| Field | 1.41 | 1.44 |
|---|---:|---:|
| `npv` | −1,436.63 | −1,547.29 |
| `inflation_leg_npv` | −58,734.94 | −58,845.61 |
| `fair_rate` | 0.021 | 0.02103875685 |

On 1.41 both legs used the same whole-month lagged period (exactly 3.000
years), so the trade repriced at the 2.10% quote whatever its exact dates. On
1.44 the fixed leg accrues 1097 days (helper) against 1095 (trade), and the
fair rate is 2.10% × 1097/1095 = 2.10388%. Setting `maturity_date: 2028-01-17`
gives a `fair_rate` of exactly 0.021 on both versions. Verdict: upstream bug
fix (1.42) [^2451].

`observation_interpolation: AsIndex` keeps working in 0.11.0 (QuantLib
deprecates the underlying option but still supports it).

### 2.5 Hull-White calibration of mean reversion and volatility together

**Who is affected.** A `SwaptionModelSpec` with `model_type: HullWhiteLattice`,
`param_mode: Calibrate` and `hw_calibration.calibrate_a: true` together with
`calibrate_sigma: true` (the defaults), on `/price-swaption` and
`/calibrate-swaption-model`. Lattice pricing with explicit `a` and `sigma`
(`tests/version_diff/probes/price-swaption/swaption_bermudan_hull_white_lattice_explicit.json`,
`..._american_..._explicit.json`) is unchanged, and calibrating sigma alone
with `a` fixed gives identical results on both versions.

**Fields that move.** `swaptions[].used_hw_a`, `used_hw_sigma`,
`used_hw_rmse`, `npv`; `hw_a`, `hw_sigma`, `rmse` on
`/calibrate-swaption-model`.

**Worked numbers.** `tests/version_diff/probes/price-swaption/swaption_bermudan_hull_white_lattice_calibrated.json`
(Bermudan on an ATM matrix, 50-step lattice):

| Field | 1.41 | 1.44 |
|---|---:|---:|
| `used_hw_a` | 0.00012218856 | 0.000278081655 |
| `used_hw_sigma` | 0.006621428597 | 0.006631481998 |
| `used_hw_rmse` | 0.019025723539 | 0.019048784649 |
| `npv` | 8,400.92 | 8,415.43 |

The two `/calibrate-swaption-model` cases
(`examples/data/vol/hwcal_eur_atm_matrix_roundtrip.json` and the probe
`hull_white_calibration_a_and_sigma.json`) move `hw_a` by 1e-12
(0.049999969128 → 0.049999969129): same mechanism, but there the objective is
not flat.

**Why.** QuantLib 1.44 rewrote the root-finding of the Jamshidian swaption
engine, which Quantra uses for the calibration helpers; its prices move at the
1e-10 level. The calibration objective is almost flat in the mean reversion
`a`: with `a` fixed at either of the two values above and sigma re-calibrated,
both versions agree exactly and the fit error is 0.0190161 against 0.0190308
— a 2.3× change in `a` moves the fit by 0.08%. Both joint optima are worse than
either sigma-only fit, i.e. the Levenberg–Marquardt search stops early on a
plateau and the stopping point is decided by noise. If you need stable
mean-reversion across versions, fix `a` (`calibrate_a: false`, `a_init` as the
value) and calibrate `sigma` only.

**Verdict:** upstream numerical change (1.44) [^2664]. Neither number is more
accurate.

### 2.6 American equity options whose exercise window starts after the valuation date

**Who is affected.** `exercise_type: EquityAmericanExercise` with
`exercise.start_date` later than `pricing.as_of_date`. Quantra prices American
and Bermudan equity options on the finite-difference engine. The control with
the window starting at the valuation date
(`tests/version_diff/probes/price-equity-option/equity_american_put_fd_control.json`)
and the Bermudan (`equity_bermudan_call_fd.json`) are unchanged; so are the
other 21 equity-option cases.

**Fields that move.** `options[].npv`, `delta`, `gamma`, `theta`,
`implied_volatility`.

**Worked numbers.** `tests/version_diff/probes/price-equity-option/equity_american_put_fd_exercise_starts_after_as_of.json`
(put, strike 100, valuation 2025-01-15, exercisable 2025-07-15 to 2026-01-15):

| Field | 1.41 | 1.44 |
|---|---:|---:|
| `npv` | 6.737683331519 | 6.71301621179 |
| `delta` | −0.426155423128 | −0.421723743332 |
| `gamma` | 0.021403985526 | 0.020655158508 |
| `theta` | −2.802025226818 | −2.666598515624 |
| `implied_volatility` | 0.199999898558 | 0.199999964179 |

The NPV falls 0.37%. Moving `exercise.start_date` to 2026-01-14, the day
before expiry, shows the mechanism: 1.41 still returns 6.7377, the fully
American price, while 1.44 returns 6.4598, next to the European twin
(`EquityEuropeanExercise`, 6.4580 on both versions).

**Why.** Up to 1.41 the finite-difference engine allowed early exercise from
the valuation date whatever `start_date` said. From 1.42 the American exercise
condition applies only from `start_date`.

**Verdict:** upstream bug fix (1.42) [^2449]. 1.41 ignored the start of the
exercise window.

### 2.7 Bond yield, durations and convexity

**Who is affected.** `pricing.options.bond_pricing_details: true` on
`/price-fixed-rate-bond`, `/price-zero-coupon-bond` and
`/price-floating-rate-bond` (the yield is solved from the price). `npv`,
`clean_price`, `dirty_price` and `bps` are unchanged; the 16 catalog fixed-rate
bonds, which return `npv` only, are unchanged.

**Fields that move.** `bonds[].yield`, `macaulay_duration`,
`modified_duration`, `convexity` — by at most 6e-9 in yield (1.8e-7 relative)
and 1.2e-6 in convexity.

**Worked numbers.** `examples/data/bonds/zcb_eur_1y_par.json`: `yield`
0.029907243586 → 0.029907247953; the exact analytic yield of this bond is
0.029907247953, so 1.41 was 4.4e-9 off and 1.44 is within 2e-13.
`modified_duration` 0.965640890613 → 0.965640886519, `convexity`
1.870062192746 → 1.870062176886. The largest move in the corpus,
`tests/version_diff/probes/price-fixed-rate-bond/frb_7y_premium_semiannual_yield_duration_convexity_bps.json`:
`yield` 0.031516471148 → 0.031516475944, `convexity` 43.14242978888 →
43.142429237193.

**Why.** The derivative used by the yield solver had the wrong sign and scale
up to 1.42, so the Newton step stopped a few 1e-9 away from the root while
still inside the solver's tolerance. From 1.43 the yields are the exact roots;
durations and convexity follow the yield.

**Verdict:** upstream bug fix (1.43) [^2589], at solver-tolerance level.

### 2.8 OIS curve helpers: the fixed-leg payment convention is now honoured (not observed in the corpus)

**Who is affected.** `OISHelper` / `DatedOISHelper` pillars whose `calendar`
(the payment calendar) differs from the overnight index's calendar, with
`payment_lag: 0` and a `fixed_leg_convention` other than `ModifiedFollowing`.
With a payment lag the convention never acts (the lag is applied with
`Following`), and with the same calendar the schedule date is already
adjusted, so none of the corpus requests could move — the four
`fixed_leg_convention` / `payment_lag` probes under
`tests/version_diff/probes/price-ois-swap/` use `TARGET` helpers on a `TARGET`
index and are bit-identical.

**Fields that move.** Every pillar of the bootstrapped curve, hence `npv`,
`fair_rate`, `legs[].flows[].discount` of anything priced on it.

**Demonstration (outside the corpus).** ESTR helpers with `calendar:
UnitedStatesGovernmentBond`, `payment_lag: 0`, valued 2025-05-28 so that the 2Y
accrual end is Memorial Day 2027-05-31: with `fixed_leg_convention: Following`
14 pillars move by up to 9.5e-6 in discount factor. `Preceding` and
`ModifiedPreceding` variants of the same request fail on 1.44 with the
payment-date error of section 3.2 instead.

**Why.** Up to 1.43 the fixed leg of the helper's internal swap ignored the
payment convention passed as `fixed_leg_convention` and used the overnight
schedule's `ModifiedFollowing`; 1.44 applies the convention you send. This is
not the cause of the cross-currency moves in 2.1 (verified by re-running those
examples with the index calendar on the leg).

**Verdict:** upstream bug fix (1.44) [^2649]. If you send a non-default
`fixed_leg_convention` on helpers paid on a foreign calendar without a lag,
0.11.0 is the first release that uses it.

### 2.9 Noise

Two cases differ only within the 1e-12 relative threshold:
`examples/data/swaption/swpt_eur_1y5y_payer_cash_par_yield.json` (5.5e-12
absolute) and `examples/data/inflation/zciis_eur_10y_payer_linear_obs.json`
(4.9e-10 absolute, 1.1e-13 relative). Floating-point noise from the rebuilt
library; no mechanism.

## 3. New errors

Two requests that returned 200 on 0.10.0 return 422 on 0.11.0. No error
disappeared.

### 3.1 A spot-starting swap valued on a holiday of the helpers' calendar

**Who is affected.** `pricing.as_of_date` on a holiday of the curve helpers'
calendar, with `DepositHelper` pillars whose `fixing_days` is greater than 0
(and swap helpers on the same curve). Any endpoint using such a curve
(`/price-vanilla-swap`, `/price-fra`, bonds, `/bootstrap-curves`) is affected
the same way.

**Worked case.** `tests/version_diff/probes/price-vanilla-swap/vanilla_as_of_on_target_holiday.json`
(as-of 2025-05-01, a TARGET holiday; deposit helpers with `fixing_days: 2`):

- 0.10.0: HTTP 200, `npv` 7e-12, `fair_rate` 0.03, first accrual 2025-05-06.
- 0.11.0: HTTP 422, `1st iteration: failed at 1st alive instrument, pillar
  August 5th, 2025, maturity August 5th, 2025, reference date May 1st, 2025:
  Missing no-fix3M Actual/360 fixing for April 30th, 2025`.

The control on a business day
(`vanilla_as_of_on_business_day_control.json`, as-of 2025-04-30) is unchanged.

**Why.** From 1.44 the deposit and swap helpers count their settlement days
from the *actual* valuation date even when it is a holiday, instead of first
rolling it to the next business day. Here spot becomes 2025-05-05 (1.41 used
2025-05-06, after rolling the valuation date to 05-02 — the wrong spot date),
and the 3M deposit's fixing date, two business days before spot, is 2025-04-30,
which is before the valuation date, so QuantLib asks for a historical fixing.
`no-fix3M` is QuantLib's internal index inside the deposit helper: it is not one
of your `pricing.rates.indices[]`, so the API has no way to supply that fixing
today (adding a 2025-04-30 entry to the `fixings` of `EUR_6M` leaves the 422).

**What to do.** Value on a business day, or set `fixing_days: 0` on the
`DepositHelper` pillars (then both versions return 200 with identical numbers,
which also shows that the swap helpers of this request did not move). A way to
pass the deposit fixing is a known gap and may be added in a later release.

Since 0.13.1 the engine detects the condition when the pillar is built and
answers `400` naming the pillar, the date, the calendar and both remedies
(`rates.curves['discount'].points[0] (DepositHelper): the evaluation date
2025-05-01 is not a business day of the helper's calendar TARGET and
fixing_days is 2 … Value on a business day of TARGET, or set fixing_days: 0
on the DepositHelper`) instead of the opaque 422 above; the date is not
rolled. See `docs/http-api.md`, "Curve helpers and the valuation date".

Verdict: upstream behaviour change (1.44) [^2653] plus a Quantra limitation.

### 3.2 An overnight coupon paid before its accrual end

**Who is affected.** An overnight leg (`/price-ois-swap`, `/price-basis-swap`,
`/price-cross-currency-swap`, a swaption's OIS underlying) whose
`payment_calendar` / `payment_convention` put a payment date before the
accrual end, and OIS helpers whose `fixed_leg_convention` does the same (see
2.8). `payment_lag` cannot be negative on any version (400), so the only
trigger is a `Preceding`-type convention on a payment calendar that does not
contain the schedule's end date.

**Worked case.** `tests/version_diff/probes/price-ois-swap/ois_overnight_payment_date_before_accrual_end.json`
(TARGET schedule ending 2025-07-04, `payment_calendar:
UnitedStatesGovernmentBond`, `payment_convention: Preceding`, so the payment
date is 2025-07-03):

- 0.10.0: HTTP 200, with bare `inf` for `swaps[0].npv` and for the coupon's
  `amount` and `rate` (the body was not strict JSON).
- 0.11.0: HTTP 422, `Payment date cannot be earlier than accrual end date`.

The control with `Following` (payment 2025-07-07,
`ois_overnight_payment_date_after_accrual_end_control.json`) is unchanged.

**What to do.** Use `Following` or `ModifiedFollowing` for the payment
convention, or a payment calendar that contains the schedule's dates, so that
every payment date is on or after its accrual end.

Verdict: upstream behaviour change (1.42) [^2421]; a non-finite answer became
an error.

## 5. Upstream changes with no observed effect

Each of these release-note items (QuantLib 1.42–1.44) has a probe in
`tests/version_diff/probes/`; the probe returned 200 with bit-identical bodies
on both versions. They may still reach a request shape not in the corpus.

- End-of-month handling in OIS and swap rate helpers [^2459] (4 probes, spot on
  a month end with `end_of_month: true`).
- `DatedOISHelper` with `settlement_days` [^2481].
- `bootstrap_trait: Discount` with `interpolator: Linear` [^2491].
- Accrued amount of simple-averaging overnight coupons [^2427] (seasoned
  mid-period OIS with `averaging_method: Simple`).
- Backward schedule with a short first period [^2511].
- Swap helpers with `calendar: UnitedKingdom` on a `TARGET` index [^2611].
- Zero-annuity guards in fair rate / fair spread [^2678] [^2690] [^2692] —
  swaps entirely in the past return 200 with `npv: 0.0` and no `fair_rate` /
  `fair_spread` on both versions (Quantra computes the fair values itself and
  drops non-finite ones).
- Callable bond with a call date on a coupon date [^2748]; trinomial-tree
  branching, Hull-White `r0` on relink and tree stepback [^2615] [^2592] [^2745]
  (explicit-parameter lattice swaptions, callable and puttable bonds).
- SABR swaption-cube calibration preserving ATM vols [^2656]
  (`calibrate-swaption-vol`, 5 cases unchanged).
- `basisPointValue` convexity term [^2769] — Quantra's `bps` is the curve-based
  BPS, not the yield-based one.
- 1.44 fixes to the American-option analytic approximations: Quantra prices
  American and Bermudan equity options on the finite-difference engine, which
  is unaffected (zero-rate, negative-rate and tiny-vol probes unchanged).

Items the API cannot reach at all (no request shape triggers them): fixed-tenor
inference with an explicit termination date [^2480] (helpers are tenor-based);
callable-bond call price during an ex-coupon period [^2455] (no ex-coupon
fields); spread-curve initial guess [^2495]; callable-bond effective
duration/convexity [^2671] (not in the response); `SimpleThenCompounded` /
`CompoundedThenSimple` yields [^2667] (every yield convention other than
`Compounded` is a 422 on both versions); overnight-index futures [^2726]
(`FutureHelper` is IBOR-only); jumps on probability curves [^2771]; the new
`Malaysia` and `Philippines` calendars (not in the `Calendar` enum).

## 6. Run the same comparison on your own requests

The tool that produced these numbers ships in the repository
(`tools/version_diff/quantra_version_diff.py`, Python 3 + `requests`; see
[`tools/version_diff/README.md`](../../tools/version_diff/README.md)). Start
the two released images side by side and point it at a directory of your own
request files (first-level sub-directory = endpoint):

```bash
docker run -d --rm --name quantra-old -p 8091:8080 ghcr.io/joseprupi/quantra-server:0.10.0
docker run -d --rm --name quantra-new -p 8093:8080 ghcr.io/joseprupi/quantra-server:0.11.0

python3 tools/version_diff/quantra_version_diff.py \
  --old http://localhost:8091 --new http://localhost:8093 \
  --requests my_requests/ --md-out diff.md --json-out diff.json
```

Run it once with `--old` and `--new` on the same server first to confirm a
zero noise floor. `--catalog` replays the functional catalog from a checkout;
`--fail-on-change` makes it usable as a gate. The report lists every changed
field with both values; `tools/version_diff/causes.json` maps each pattern
above (endpoint, fields, triggering request feature) to its explanation and
upstream reference, so a change in your report can be matched to a section of
this page. Request shapes and field names are documented in
[`http-api.md`](../http-api.md).
